# Plan: Production Directory Restructure

**TL;DR:** Consolidate into four clean top-level layers with minimal logic rewrites — mostly file locations and imports move. The key insight is separating *what you never touch* (`core/`) from *what you add to* (`collectors/`, `applications/`).

## What Gets Generated (and why)

### `utils/build/esi_codegen.py` → `core/esi/generated/`

The **low-level ESI client engine**. Reads the OpenAPI spec snapshot and writes:
- `manifest.py` — `OPERATIONS` dict (208 ops), `OPERATIONS_BY_TAG`, `ALL_SCOPES`, `COMPATIBILITY_DATE`
- `client.py` — `execute_operation(op_id, path_params, token, ...)` + `fetch_all_pages()` — the generic call engine that constructs URLs, handles auth headers, paginates
- `schemas.py` — TypedDict stubs from OpenAPI schema definitions
- `operations.py` — per-operation typed wrappers (thin convenience layer over `execute_operation`)

This is the **execution layer** — it knows *how* to call any ESI endpoint but doesn't know *when* or *why*.

### `utils/build/domain_codegen.py` → `collectors/personal_generatedESI|corp_generatedESI|public_generatedESI/`

The **typed domain collector wrappers**. Reads `OPERATIONS` + `OPERATIONS_BY_TAG` from the generated manifest and writes:
- One `.py` file per ESI tag per scope (e.g., `collectors/personal_generatedESI/assets.py`, `collectors/corp_generatedESI/wallet.py`, `collectors/public_generatedESI/market.py`)
- Each file contains typed Python functions like `get_characters_character_id_assets(character_id: int, token: str) -> list`
- These functions call `execute_operation()` / `fetch_all_pages()` from `core/esi/generated/client.py`

This is the **domain API** — application code and workers import from here, never from `core/esi/generated/` directly.

### CLI (via build.py → utils/build/)

```powershell
python build.py                      # full pipeline: spec fetch + client codegen + collectors
python build.py --spec-only          # just fetch latest ESI OpenAPI spec
python build.py --gen-only           # just regenerate core/esi/generated/
python build.py --collectors         # just regenerate collectors/personal_generatedESI|corp_generatedESI|public_generatedESI/
python build.py --force              # overwrite even if already current
python build.py --date 2025-12-16    # pin to specific compatibility date
```

## `core/queue/` — The Queue Module

The queue module is split by concern. Currently `task_queue.py` and `rate_limiter.py` are tangled
monoliths that each do 3+ jobs. This restructure separates them cleanly:

### `scheduler.py` — Task Lifecycle
- `Task` class (id, owner, name, status, timestamps)
- Two `ThreadPoolExecutor` pools: public lane, private lane (each single-threaded, FIFO)
- `enqueue()`, `get_task()`, `get_tasks_for_owner()`, `cancel_task()`, `clear_tasks()`
- Future: periodic/scheduled task support (cron-like recurring collection jobs)

### `esi_req.py` — ESI Request Pipeline
Per the [ESI rate limiting spec](https://developers.eveonline.com/docs/services/esi/rate-limiting/):

- **Floating window token buckets** — per `(rate_limit_group, applicationID:characterID)` pair. Each bucket tracks consumed tokens in a sliding window (typically 150 tokens / 15 minutes).
- **Token costs** — 2XX=2, 3XX=1, 4XX=5, 5XX=0 tokens.
- **Per-group bucket management** — dynamically created from `X-Ratelimit-Group` response headers; pre-seeded for endpoints that omit the header (structures, etc.). Default bucket (limit=1800, window=900s) for ungrouped routes.
- **Lane alternation** — `_FairAlternatingLock` ensures strict one-for-one interleaving between public and private ESI worker threads when both are active.
- **Response caching** — URL-pattern-based TTL cache for expensive endpoints (structure info=7d, structure markets=30m).
- **429/420 handling** — respects `Retry-After` header; backs off on error rate limit (older ESI system: 100 non-2xx/3xx per minute → 420 on all routes).
- Exports: `esi_request()`, `esi_get()`, `esi_post()`, `set_request_lane()`, `get_esi_rate_limiter()`.

### `streams.py` — Event Streaming (SSE)
- `_ThreadRoutedWriter` — replaces `sys.stdout`/`sys.stderr`; routes worker-thread output to task logs
- `_TaskLogHandler` — routes `logging` records to current task
- `_esi_rate_hook` — fires after each ESI request, updates task's rate stats
- `rate_stream()` — SSE generator: limiter stats + task briefs
- `log_stream(task_id)` — SSE generator: per-task log lines + rate events + done sentinel

### `writer.py` — DB Write Queue (future)
DuckDB is single-writer. A serialized write channel would prevent concurrent thread collisions.
Not implemented yet, but the slot exists for when it's needed.

### Other Potential Queue Concerns (future)
- **Scheduled tasks** — cron-like periodic collection ("refresh markets every 30 min")
- **Event bus** — formalized pub/sub so applications can publish custom SSE events

## `core/db/` — Modular Database Layer

### Why split models into a `models/` package?

New collectors and applications will add DuckDB tables. If everything is in one `models.py`, that file becomes an ever-growing dump. Split by data domain so each concern is isolated:

| File | Tables | Who creates them |
|---|---|---|
| `models/identity.py` | `users`, `site_admins` (DuckDB) + `characters` (SQLite) | `core/db/__init__.py` at startup |
| `models/market.py` | `market_orders`, `market_structures`, `market_region_cooldowns`, `isk_per_hour_results` | `core/db/__init__.py` at startup |
| `models/structures.py` | `structures` (with all cooldown columns) | `core/db/__init__.py` at startup |
| `models/sde.py` | All `dim_*` + `fact_*` + `sde_manifest` + `sde_dataset_manifest` tables | `collectors/sde_loader.py` during SDE rebuild |
| `models/registry.py` | `esi_registry_*`, `esi_routes`, `esi_route_parameters`, `esi_schemas`, `esi_scopes` | `core/esi/registry.py` during spec sync |

**Convention for new tables:** When a collector or application needs a new DuckDB table, add a new model file (or extend an existing domain file). The DDL lives in the model file; `publicDB.py` discovers and runs it at startup.

### `core/db/__init__.py` — Initialization

Absorbs what was `workers/publicData/DatabaseInit.py` + `db/database.py` init logic:
- `ensure_data_dirs()` — creates `_publicData/` and `_privateData/` if missing
- `ensure_public_database()` — runs all DDL from `models/` against DuckDB
- `initialize_private_database(owner_id)` — creates per-owner SQLite with WAL mode, PRAGMA settings
- Called synchronously at startup from `main.py`

### `publicDB.py` and `privateDB.py`

- `publicDB.py` — `connect()`, all DuckDB CRUD helpers (upsert_market_orders, search_market_orders, upsert_structures, link_public_user, etc.)
- `privateDB.py` — `get_private_session(owner_id)`, engine/session factory caching

## Key Constraints

- All ESI HTTP goes through `core.queue.esi_req` — never raw `requests` from collectors or applications
- Applications import **only** from `core.plugin.adapters` (never from `core.db`, `core.esi`, or `core.queue` directly)
- Generated code lives in `core/esi/generated/` and `collectors/personal_generatedESI|corp_generatedESI|public_generatedESI/` — never hand-edit
- DuckDB connections are per-thread — `core.db.publicDB.connect()` returns a fresh connection each call
- Token lifecycle (load, refresh, pick, resolve owner) all lives in `core.esi.auth`
- New DuckDB tables: add model file to `core/db/models/`, DDL auto-discovered at startup
- New collector domain: add subdirectory to `collectors/` (e.g., `collectors/contracts/`)
- New application: add subdirectory to `applications/` with `BaseTool` subclass — auto-discovered

## Collector Convention

A **collector** is a module that orchestrates: fetch (ESI) → transform → store (DuckDB/SQLite).
Collectors are organized by **data domain** — each domain gets its own subdirectory under `collectors/`.

### Structure

```
collectors/
├── sde_loader.py                ← special: standalone SDE pipeline (no domain subdir needed)
├── market/                      ← domain: market orders
│   ├── __init__.py              ← exports enqueueable entry points
│   ├── publicRegions.py         ← worker: sweep all regions for public orders
│   └── privateStructures.py     ← worker: fetch authenticated structure orders
├── structures/                  ← domain: player structures
│   ├── __init__.py
│   └── publicDiscovery.py       ← worker: seed IDs + enrich metadata
├── contracts/                   ← (future) domain: public/personal contracts
├── killmails/                   ← (future) domain: killmail collection
├── personal_generatedESI/       ← AUTO-GENERATED typed ESI wrappers (character-scoped)
├── corp_generatedESI/           ← AUTO-GENERATED typed ESI wrappers (corp-scoped)
└── public_generatedESI/         ← AUTO-GENERATED typed ESI wrappers (unauthenticated)
```

### Rules

1. **One domain = one subdirectory.** Name it after the data it collects (market, structures, contracts), not after the ESI endpoint or the auth method.
2. **Workers are enqueueable.** Each worker module exposes a top-level function (e.g., `fetch_all_market_data()`, `discover_structures()`) that can be passed to `enqueue()`.
3. **Imports.** Collectors import ESI HTTP from `core.queue.esi_req` (or use the typed wrappers from `collectors/personal_generatedESI|corp_generatedESI|public_generatedESI/`). They write to DuckDB via `core.db.publicDB` or to private SQLite via `core.db.privateDB`.
4. **`__init__.py` as the public API.** Each domain's `__init__.py` re-exports the entry-point functions. Workers enqueue via `from collectors.market import refresh_region`.
5. **AUTO-GENERATED packages are read-only.** `collectors/personal_generatedESI|corp_generatedESI|public_generatedESI/` are regenerated by `domain_codegen.py`. They are *API wrappers*, not orchestrating collectors. The hand-written domain collectors call *into* them.
6. **`sde_loader.py` is the exception.** It's a standalone pipeline (download zip → parse YAML → build warehouse). It doesn't follow the domain-subdirectory pattern because there's only one SDE and it's not a recurring ESI collector.

### Adding a New Collector Domain

```python
# 1. Create the domain directory
# collectors/contracts/__init__.py
from collectors.contracts.public import fetch_public_contracts

# 2. Create worker module(s)
```
